## P0: 核心闭环 — 让系统端到端真正可用

> 目标：游戏内金币变动写回数据库，房间管理完整，服务端7x24稳定运行。

### P0-1 金币持久化结算

**问题**：当前游戏内 `player.score` 仅在内存中，游戏结束后未写回 `users.gold`。

**任务**：
1. 在 `src/lib/` 新建 `goldManager.ts`，封装金币增减操作（带事务、带流水记录）
2. 接口：`addGold(userId, amount, reason, refId)` / `deductGold(userId, amount, reason)`
3. 写入 `chip_transactions` 表（流水审计）
4. 在各游戏 `settle()` 中调用：开局扣底注/下注，结算赔付
5. 下注时校验余额不足则拒绝

**验收**：
- 测试账号登录→进入游戏→下注→结算→退出→重新登录，金币数值正确
- `chip_transactions` 表有对应流水记录
- 余额不足时下注返回明确错误

### P0-2 房间管理器完善

**问题**：`RoomManager` 当前是占位实现，未与游戏实例联动。

**任务**：
1. 完善 `src/lib/roomManager.ts`：创建房间/加入/离开/解散
2. 房间状态机：waiting → playing → settled
3. 房间与游戏实例绑定（roomId → gameInstance）
4. 玩家离线自动离开房间，游戏中离线托管/结算
5. 房间列表查询接口（HTTP `/api/rooms`）

**验收**：
- 创建房间→2人加入→开始游戏→游戏中一人断线→游戏继续/结算正常
- 房间列表接口返回正确状态

### P0-3 服务端稳定性加固

**任务**：
1. 全局异常捕获（WS消息处理try-catch已存在，HTTP补充）
2. 游戏定时器泄漏检查（ArcadeGame的setTimeout在房间销毁时clear）
3. 数据库连接池监控（SQLite WAL模式，并发写入处理）
4. 内存泄漏检查（游戏实例销毁时从gameInstances移除）
5. 优雅关闭（SIGTERM时保存状态、关闭WS、关闭DB）
6. 日志分级（info/warn/error，写入文件+控制台）

**验收**：
- 连续运行100局游戏无内存增长（RSS稳定）
- 异常消息不导致进程崩溃
- 优雅关闭后重启数据不丢失

### P0-4 端到端冒烟测试脚本

**任务**：
1. 编写 `tests/e2e_smoke.js`：注册→登录→WS连接→创建房间→加入→开始→下注→结算→查询金币→退出
2. 覆盖3类游戏各1款（WZMJ/QZNN/BCBM）
3. 断言金币变化正确
4. CI可重复运行

**验收**：`node tests/e2e_smoke.js` 全部通过，输出金币变化对账表。

## P4: 生产部署 — 上线准备

### P4-1 服务器环境

**任务**：
1. 准备Linux服务器（Ubuntu 22.04+，2C4G起步）
2. 安装Node.js 18+、SQLite（或迁移MySQL）、Nginx
3. 防火墙配置（80/443/WS端口）
4. 域名解析+SSL证书（Let's Encrypt）

### P4-2 部署架构

```
                    Nginx (443)
                   /    |    \
            静态前端  管理后台  API代理(:8000)
                                   |
                              Node服务端
                             /    |    \
                         HTTP   WS(10000)  SQLite
```

**任务**：
1. 前端构建产物scp到 `/opt/728/web/`
2. 服务端 `node scripts/build.js` 后 `dist/` 部署到 `/opt/728/server/`
3. PM2管理Node进程（`pm2 start dist/index.js --name 728-server`）
4. Nginx配置：静态文件+API反向代理+WS upgrade
5. 数据库文件 `/opt/728/data/728.db`，定时备份（cron每天备份）

### P4-3 压力测试

**任务**：
1. 用 `artillery` 或 `k6` 模拟100并发WS连接
2. 模拟50桌同时游戏，观察CPU/内存/延迟
3. SQLite写入瓶颈测试（如不足，评估迁移MySQL）
4. 输出性能报告，确定服务器配置上限

### P4-4 数据迁移评估（可选）

**任务**：
1. 评估SQLite → MySQL的迁移成本（用户量>1000或并发>50时建议）
2. 编写迁移脚本（schema.sql → MySQL语法，数据导出导入）
3. `sqliteDb.ts` → `mysqlDb.ts` 适配层（保持相同API）
